# 栗子杯 V1 正式项目开发里程碑与新会话交接

> 文档用途：供新的 Codex 会话直接接手栗子杯 V1 正式项目开发。  
> 编写日期：2026-08-13  
> 当前状态：静态视觉原型已完成；正式项目尚未开始。  
> 开发原则：分阶段实现，每个阶段达到完成门槛后再进入下一阶段。

## 1. 新会话的首要目标

新会话从 **Phase 0：项目骨架** 开始正式开发，不要一次性实现完整 V1。

正式项目应在当前工作区根目录内建立清晰的前后端边界：

```text
Kuriboh/
├─ frontend/                 # Vue 3 正式前端
├─ backend/                  # FastAPI 正式后端
├─ docs/                     # 项目文档
├─ static-preview/           # 已确认的页面视觉原型，必须保留
├─ sites-preview/            # Sites 部署包装，仅用于预览，不是正式项目
├─ 栗子杯网站开发文档.md       # 业务与实现基线
└─ README.md                 # 正式项目启动与开发说明
```

除非用户在新会话中明确扩大范围，否则第一个开发会话只完成 Phase 0，不提前实现赛事业务。

## 2. 需求与设计基线的优先级

开发时按以下优先级处理冲突：

1. 用户在当前开发会话中的明确指令。
2. `栗子杯网站开发文档.md` 中已经确认的业务规则。
3. 本文档中的里程碑、交接说明和开发约束。
4. `docs/DESIGN.md` 中的视觉设计系统。
5. `static-preview/` 中已经确认的页面结构、信息层级和视觉表现。
6. 其他实现建议。

不得为了简化实现改变已经确认的赛事规则、状态锁定规则或权限边界。

## 3. 正式项目必须使用现有预览页面作为开发基线

### 3.1 强制使用的预览文件

正式前端页面必须以当前目录中的以下文件为视觉与页面结构基线：

```text
static-preview/index.html
static-preview/styles.css
static-preview/script.js
```

辅助参考截图位于：

```text
static-preview/preview-home.png
static-preview/preview-tournaments.png
static-preview/preview-detail.png
static-preview/preview-live-detail.png
static-preview/audit-*.png
```

这些文件代表已经确认的：

- 品牌色、背景色、边框色和基础视觉风格；
- 顶部导航、页面最大宽度和间距体系；
- 首页、赛事中心和赛事详情的信息架构；
- 报名中赛事与进行中赛事的不同页面状态；
- 当前对阵、正式排名、赛事进程和报名卡片的布局方向；
- 桌面优先、克制、信息型的产品风格。

### 3.2 正式开发中的使用方式

正式前端使用 Vue 3 实现时，应当：

- 将预览页面拆分为 Vue 路由、视图和可复用组件；
- 将预览中的颜色、间距、字号、圆角和边框整理为设计 Token；
- 将测试数据替换为类型明确的 API 数据；
- 将静态页面切换替换为 Vue Router；
- 将静态交互替换为真实状态和接口调用；
- 保留已经确认的信息层级和整体视觉方向；
- 新页面复用同一套组件和设计 Token，不重新发明另一套视觉风格。

正式项目 **不得**：

- 使用 `iframe` 嵌入 `static-preview/index.html` 作为正式页面；
- 直接在 `sites-preview/` 内继续开发正式项目；
- 丢弃预览稿后重新生成一套无关的通用后台或 AI 风格界面；
- 把全部页面合并成难以维护的单个万能组件；
- 删除 `static-preview/`，该目录需要作为后续视觉回归基线保留。

### 3.3 `sites-preview/` 的定位

`sites-preview/` 只是为了把静态原型部署到 Sites 而建立的包装项目，其中 `public/prototype/` 是预览文件的副本。

- 它不是 Vue 3 + FastAPI 正式项目的起点。
- 不要从其 Next/Vinext 包装结构推导正式项目架构。
- 正式开发以根目录新建的 `frontend/`、`backend/` 为准。
- 默认不进行 Sites 构建或部署；只有用户明确要求“部署、发布或更新 Sites”时才能执行。

## 6. 正式项目技术基线

根据 `栗子杯网站开发文档.md`，正式项目采用：

### 前端

- Vue 3；
- TypeScript；
- Vue Router；
- 独立的 API、Store、View、Component 和 Type 边界；
- 从 `static-preview/` 提取的统一设计 Token 和组件。

### 后端

- FastAPI；
- PostgreSQL；
- SQLAlchemy；
- Alembic；
- Pydantic 请求与响应模型；
- 清晰的 router / schema / service / repository 分层。

### 测试

- 后端业务规则单元测试；
- API 集成测试；
- 瑞士轮配对与排名独立测试；
- 前端关键状态与交互测试；
- 最终完整流程 E2E 验收。

关键状态和权限必须由后端验证，不能仅依赖前端禁用按钮。

## 7. 分阶段开发里程碑

## Phase 0：项目骨架

### 目标

建立可维护、可启动、可测试的正式项目基础，不提前实现完整业务。

### 交付内容

- 创建 `frontend/` Vue 3 + TypeScript 项目；
- 创建 `backend/` FastAPI 项目；
- 配置 PostgreSQL；
- 配置 SQLAlchemy 与 Alembic；
- 建立 `.env.example`，不写入真实密钥；
- 建立统一配置、日志和错误响应结构；
- 建立角色与权限基础边界；
- 完成前后端健康检查联通；
- 建立基础测试命令；
- 建立根目录 `README.md`；
- 从 `static-preview/styles.css` 提取第一版设计 Token；
- 在 Vue 中建立页面壳、顶部导航和基础响应式布局；
- 建立正式路由占位，但不伪造完整业务功能。

### 完成门槛

- 全新环境可按 README 启动前端、后端和数据库；
- Alembic 可从空数据库执行；
- 前后端健康检查成功；
- 测试命令可运行；
- 首页页面壳与现有预览视觉方向一致；
- 没有把静态原型作为 iframe 嵌入；
- 没有开始实现 Phase 1 以后的业务。

## Phase 1：账号与内容基础

### 交付内容

- 手机号或 QQ 号 + 密码注册与登录；
- 修改密码；
- USER / PLATFORM_ADMIN；
- QQ OAuth 接口边界和账号绑定流程；
- 个人中心；
- 禁卡表版本管理；
- 平台公告；
- 基础图片上传；
- 对应前台和管理员页面。

### 完成门槛

- 手机号和 QQ 号作为登录标识均唯一、昵称唯一；
- 密码只保存安全哈希；
- 普通用户无法调用管理员 API；
- 禁卡表版本递增正确；
- 富文本经过安全清洗；
- 账号、权限、版本和内容安全均有测试。

## Phase 2：赛事、报名与开赛

### 交付内容

- 创建赛事草稿；
- 发布赛事并立即开放报名；
- 报名、取消报名、审核和恢复；
- USER 与 PLATFORM_ADMIN 均可报名；赛事创建者报名仍需审核并受容量限制；
- 容量限制；
- 待审核报名阻断开赛；
- 正式参赛名单快照；
- 开始赛事后锁定核心配置；
- 将报名中赛事预览页面接入真实数据。

### 完成门槛

- `栗子杯网站开发文档.md` 第 21 章场景 2～4 全部通过；
- 并发审核不会超过最大参赛人数；
- 赛事管理员可以完成报名且不会丢失其赛事所有权；
- 开赛后报名关闭且核心参数不可修改。

## Phase 3：瑞士轮核心

### 开发顺序

先完成并测试后端算法，再接入前端页面。

### 交付内容

- 第一轮随机配对；
- 胜场分组、下浮和跨组；
- 优先避免重复对手；
- BYE 选择与计分；
- 配对预览、重新生成、交换玩家和发布；
- 双方独立提交赛果；
- 赛果冲突与管理员裁定；
- OMW；
- 败局轮次小分；
- 正式排名快照；
- 下一轮发布后锁定上一轮；
- 瑞士轮退赛窗口；
- 将 `detail-live` 预览中的对阵、进程和排名接入真实数据。

### 必测场景

1. 偶数和奇数人数首轮。
2. BYE 记胜但不计入自己的 OMW 对手集合。
3. 同一选手原则上不重复获得 BYE。
4. 后续轮优先避免重复对手。
5. 同胜场组奇数时正确下浮。
6. 必要时跨相邻胜场组避免重赛。
7. 四种双方赛果提交组合。
8. 单方提交不自动结束。
9. 下一轮仅生成预览时，上一轮仍可纠错。
10. 下一轮发布后，上一轮不可修改。
11. 排名排序链完整且结果稳定。
12. 退赛会作废尚未发布的下一轮预览。

### 完成门槛

- 第 21 章场景 5～10 全部通过；
- 配对和排名单元测试可固定随机种子并稳定重复。

## Phase 4：淘汰赛

### 交付内容

- 从瑞士轮最终排名产生 Top N；
- 固定种子签表；
- 淘汰赛自动推进；
- 双方独立提交赛果；
- 管理员判负；
- 下一阶段发布后锁定上一阶段；
- 决赛完成后等待管理员手动结束赛事；
- 完整淘汰赛结果展示。

### 完成门槛

- 第 21 章场景 11 通过；
- Top 2、Top 4、Top 8 的典型签表路径有测试。

## Phase 5：赛事结束、卡组截图与周报

### 交付内容

- 管理员手动结束赛事；
- 全赛事结果永久锁定；
- 根据比赛结果识别最终四强；
- 四强卡组截图上传、重新上传、审核和退回；
- 四强 4/4 审核门槛；
- 模板化生成周报；
- 周报一键生成并发布，不提供管理员编辑或草稿预览；
- 周报发布后不可修改或撤回；
- 赛事中心周报列表和周报详情。

### 完成门槛

- 第 21 章场景 12～14 全部通过。

## Phase 6：消息、首页、审计与收尾

### 交付内容

- 消息中心；
- 管理员赛事通知；
- 平台通知；
- 我的赛事；
- 首页“我的当前赛事”和快捷入口接入真实数据；
- 置顶公告；
- 审计日志；
- 并发与重复点击保护；
- 文件上传安全；
- 完整 E2E 和集成验收；
- 根据真实使用情况复查视觉问题记录。

### 完成门槛

- 第 21 章全部 16 个核心验收场景通过；
- 完整跑通发布赛事至周报发布的办赛闭环。

## 8. 每个里程碑的通用完成要求

每个 Phase 结束前必须：

- 运行与本阶段相关的单元测试和集成测试；
- 验证普通用户不能访问管理员功能；
- 验证后端状态约束，不能只检查前端按钮；
- 更新 README、环境变量示例和迁移说明；
- 记录未解决问题，不用临时补丁掩盖；
- 检查桌面端和移动端的关键页面；
- 确认没有修改阶段范围之外的业务规则；
- 向用户明确汇报已完成内容、测试结果和下一阶段建议；
- 等待用户确认后再进入下一 Phase。

## 9. 新会话开始时的执行清单

新的 Codex 会话开始正式开发时，应依次执行：

1. 阅读根目录 `AGENTS.md`。
2. 阅读 `docs/DESIGN.md`。
3. 阅读本文件。
4. 阅读 `栗子杯网站开发文档.md`，重点关注第 1～6、17～21、23～26 章。
5. 检查 `docs/视觉设计待优化问题.md`，不要把暂缓问题误当成 Phase 0 阻断项。
6. 检查 `static-preview/index.html`、`styles.css` 和 `script.js`。
7. 检查工作区状态，保护用户已有文件和改动。
8. 创建正式的 `frontend/` 与 `backend/`，不在 `sites-preview/` 中开发。
9. 只执行 Phase 0。
10. 完成构建、迁移、测试和 README 验证后向用户汇报。

## 10. 新会话默认约束

- 默认不构建、不发布、不更新 Sites。
- 只有用户明确要求部署时，才使用 Sites 构建与托管流程。
- 不删除现有静态预览、截图或问题记录。
- 不把 `sites-preview/` 视为正式项目。
- 不在 Phase 0 中实现瑞士轮、淘汰赛或周报业务。
- 不在没有测试的情况下宣告某个 Phase 完成。
- 不用前端逻辑替代后端权限、容量、状态锁定和并发校验。
- 不引入 V1 明确排除的 AI 周报、卡组识别、卡组码或外部卡片数据库。

- 本地开发是否统一使用 Docker；

- 前端具体包管理器；

- 图片存储方案和生产环境限制；
- 正式生产部署方案与域名；
- 管理员初始账号的创建方式。

Phase 0 可先提供安全的默认配置和 `.env.example` 占位，不应写入或猜测真实凭据。

## 12. 当前交接结论

当前工作成果是“已经确认视觉方向和关键页面状态的静态原型”，不是正式应用。

新会话应在保留预览成果的基础上：

1. 建立 Vue 3 + FastAPI + PostgreSQL 正式架构；
2. 将预览页面逐步组件化并接入真实业务；
3. 严格按 Phase 0～6 推进；
4. 以自动化测试和第 21 章验收场景作为完成依据；
5. 默认只在本地开发，未经明确要求不操作 Sites。
